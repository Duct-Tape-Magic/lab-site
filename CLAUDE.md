# CLAUDE.md — Lab Site

## What this is

A website where students open lab procedures (rich text, photos, YouTube video, math, downloadable files) organized in a folder tree. The owner (a teacher, not a professional developer) manages everything from a hidden admin mode on the live site. Built as a static site on GitHub Pages with Supabase (Pro plan) for data, auth, and file storage. The full design rationale, capacity math, cost, and phase plan live in `docs/PLAN.md` — read it before any significant change.

**Hard requirements:** under $50/month; must stay up for 100 concurrent students; never paused for inactivity (the owner's earlier free-tier Supabase project was paused and they consider downtime an emergency); public content must survive a database outage.

## Architecture in one paragraph

Students load `index.html` from GitHub Pages. The page fetches the catalogue (folders, lab list, site text) from Supabase; if that fails after retries it falls back to `data/snapshot.json`, then to a copy cached in localStorage, then shows an editable "unavailable" message. Lab content (`lab_content` + `attachments`) is loaded lazily per lab. Public labs are read directly under RLS. Locked labs (password / accounts / admin) have their content hidden by RLS and will be served by the `gate` Edge Function (Phase 3). Files live in two buckets: `lab-files-public` (public labs, plain URLs) and `lab-files-private` (locked labs, signed URLs from `gate`; Phase 3). The admin is a Supabase Auth user with `app_metadata.role = 'admin'`; every write policy and stats function checks `is_admin()`.

## Data conventions

- IDs: `f-<ts>` folders, `l-<ts>` labs, `att-<ts>-<rand>` attachments, `g-<ts>` groups.
- Slugs are unique per table and form the URLs: `#/f/<slug>`, `#/lab/<slug>`, `#/search?q=`, `#/signin`.
- `labs` is the catalogue (safe to list). Procedure content and media live in `lab_content` (`format` = `html` from Quill, or `labtags` = a lab file rendered by `ltRender()`); files in `attachments`. Never put content in `labs`.
- Lab files: parsing is `ltProtect` (stash code/math) → `ltExtractTags` (replace `\commands` with placeholders, build widget HTML) → `marked.parse` → `ltInject` → `ltRestore`. Widgets carry `data-field` / `data-check` / `data-photo` ids; `ltBind(area, labId)` restores and autosaves student entries to localStorage (`labsite.entries.<labId>`) and photos to IndexedDB (`labsite` / `photos`). Field ids are stable as long as the author sets `id=`; auto ids are sequential per type in document order. `\graph` widgets (`ltRenderGraph`, inline SVG, expressions compiled by `ltCompileExpr`) read the live table cells and redraw on input. Report tab (2026-09-23): a `\report{…}` block (and optional `\style{…}`) is stored on `ctx.meta` by `ltExtractTags`, rendered separately by `ltRender` into `r.report`/`r.style`; `buildLabTagsHTML` builds the Procedure/Report tab bar (only when a report exists); `\answer` boxes in the report save as plain `<id>` fields through the same `ltBind`; `\usetable`/`\usegraph`/`\useanswer`/`\usephoto` mirrors are cloned/redrawn from the procedure pane by `rpPrepare`/`rpRefreshMirrors` (refreshed on input/change in the procedure pane, and once ~1s after bind so photos loaded from IndexedDB show); interactive widgets (`\answer`, `\datatable`, `\photo`, `\notes`, `\graph`) are allowed inside `\report{}` and bind through the same `ltBind`; `switchLabTab(name, btn)` scopes the tab toggle and mirror refresh to the area that owns the clicked tab (lab page vs builder preview); `previewReport()` prints the report pane via `body.report-print` CSS.
- Builder mode (2026-09-23): the lab modal's "Procedure format" select has three views — `builder` (default for new labs and for existing `labtags` labs), `labtags` (the raw lab file textarea `#lab-markup`, Import file / Apply header / Figures manager) and `html` (Quill). Builder and Lab file are two views of one text: the builder renders a block model into `#lab-builder`, and every change serializes back into `#lab-markup` (which `previewLabMarkup`, `applyLabMarkupMeta`, `labFilePaths` and `saveLab` keep reading). Saved `format` is always `labtags` for the builder. Code lives inline in `index.html` between marker comments: `// BUILDER-MODEL-BEGIN/END` (pure block model, verbatim copy of the dev module: `builderParse(text) → model`, `builderSerialize(model) → text`, `builderNewBlock(type)`, `builderTemplates`, `bm*` helpers, `BM_*` constants, mirrors of `ltParseOptions`/`ltBalanced`/`ltProtect`/`slugify` guarded by a drift test), `// BUILDER-UI-BEGIN/END` (`builderMount(container, model, onChange, host)`, `builderGetModel`, `builderSetModel`, `builderDestroy`, `bu*` helpers, `.bu-*` CSS before the mobile media query) and `// BUILDER-GLUE-BEGIN/END` (`buLabModel`, `buLastSerialized`, `builderActive()`, `buLabLoad(text)`, `buLabOnChange`, `buLabHost`, `buHeaderFromFields`, dev helper `buEquivalenceCheck(text)`). Round-trip rule: `builderSerialize(builderParse(t))` must render the same widgets as `t` (same ids, same order) and be a fixed point; anything the builder cannot represent becomes a `raw` block that re-emits byte for byte. Ids: the builder assigns a slug of the block's title (`trial-1-data`) or a dashed fallback (`question-1`) when a block is inserted; a fresh block's id follows its title until the lab is saved (`bmFreezeAll`), after which ids never change (students' saved entries hang off them). The lab modal's title/summary/tags/minutes fields are the authority for the file header on save. The renderer shares `ctx.math` with the report/style contexts (`rctx.math = ctx.math`) so math inside `\report{}`/`\style{}` renders. The dev modules and their Node test (`builder-model.test.js`, includes an inline guard that diffs the `index.html` slices against the modules) live outside the repo in the Claude scratchpad; when editing builder code, edit `index.html` directly and keep the marker slices self-contained.
- Widgets (2026-10-16, `docs/WIDGETS.md`): `\widget[type=…, id=…, table=…, …]{Instruction}` is one more block type. The single `WIDGETS` catalog in `index.html` drives the renderer (`ltWidgetBlock` → `.lt-widget[data-widget][data-widget-type][data-opts]`), `ltBindWidgets` (states idle/running/failed; passive until Start; no camera → calm note; `failed` only after a tap broke something, with the target table highlighted and a Get help button that just opens the lab's existing help box), the Builder card (`buFormWidget`, `Widget…` picker button, `wcols`/`wcol`/`whelp` kinds, `table-ref` for the target) and the admin Widgets tab (`site_content._widgets` JSON, per-type on/off; off = out of the Builder picker only). A widget owns no student data: `ltWidgetHost` (built in `ltBind` from the tables' `tableApi`) records into the target `\datatable` through the same add-row + save path as typing (first row whose target cells are all empty, else a new row when `addrows`, else Record disabled with a note). `ltStopWidgets()` releases cameras on navigation, modal close, preview re-render and `visibilitychange`. Widgets are hidden in admin read-only review and removed from the PDF/print. Ids: kind `widget` (`widget1`…), in `BM_ID_TYPES`/`BM_PIN_KINDS`.
- Media entries in `lab_content.media`: `img:<bucket path>|<alt text>` or `youtube:<id>`. `labs.cover_path` uses the same form (alt dropped). Full `http(s)` URLs are tolerated for legacy/external images.
- Storage paths: `labs/<lab-id>/<timestamp>-<rand>-<safe-name>.<ext>`; site-level uploads under `site/`. Records store bucket-relative paths; `fileUrl(path)` builds the public URL. Rich-text images inside Quill HTML are stored as full public URLs (Quill needs a `src`); `imagePathsInHTML()` maps them back for cleanup.
- Access levels on folders and labs: `inherit | public | accounts | admin`. `effectiveAccess(lab)` (client) mirrors `resolve_access()` (SQL); the SQL is authoritative. The `password` level still exists in SQL but was removed from the editor dropdowns on 2026-10-26 (its server-side gate was never built, so it only showed a dead prompt); no live rows use it.
- Status: `draft | published | scheduled` (+ `publish_at`). `lab_is_live()` in SQL, `labIsLive()` in JS.
- `site_content` holds every student-facing string (keys mirror `DEFAULTS`), plus JSON blobs `_design`, `_announcement` (`{text, link, expires}`), `_settings`.
- Every save of an existing lab inserts a `lab_revisions` row first (restore UI comes in Phase 4).
- Storage cleanup on save/delete: files under the lab's own folder that are no longer referenced are removed (`referencedPaths`, `removeStoragePaths`, `listStorageFolder`). Reference counting across labs is needed once "Save as copy" exists.
- Analytics: `logEvent()` inserts rows into `events` ONLY for signed-in students (owner's rule since 2026-09-22: visitors without an account must send nothing to the server); `visitor_id` is the student's user id; views deduplicated per lab per browser session; admins are never logged.

## JS conventions

- Global `state`: `folders`, `labs`, `content` (per-lab cache), `text`, `session`, `role`, `source` (`live | snapshot | cache | none`), `route`.
- `render()` re-renders the current route into `#view`; `renderChrome()` updates nav/footer/banners; `reloadCatalogue()` refetches and re-renders after any data change.
- `getText(key)` / `fmt(key, vars)` for all student-facing strings. Add new strings to `DEFAULTS`, `SITE_TEXT_GROUPS`, and `TEXT_LABELS` together.
- `escapeHTML()` on all data interpolated into HTML. Owner-authored Quill HTML is inserted unescaped by design.
- Quill editors are created lazily once (`labEditor`, `richTextEditor`); set `root.innerHTML` on open. Empty check: `'<p><br></p>'`.
- `uploadFile(file, folder, {compress})` compresses images client-side (max edge 1600, WebP/JPEG q0.82) before upload. HEIC cannot be decoded in Chrome; the error message tells the owner what to do.
- Errors never blank the page: `window.onerror` shows `#error-banner`; `render()` and `init()` are wrapped.


## Student-entry invariants (do not change without a migration plan)

Real student work hangs off these. Changing any of them silently orphans saved entries.
- localStorage key `labsite.entries.<labId>` for anonymous work and `labsite.entries.<userId>:<labId>` for a signed-in account; IndexedDB `labsite` / `photos` keyed `<labId>|<photoId>` (anonymous) or `<userId>:<labId>|<photoId>`; `ltKey`/`ltScope` build them. On sign-in `ltSwitchUser` moves anonymous work into that account's compartment (never overwriting). Accounts never delete each other's local work (since 2026-10-13). Supabase `lab_entries(user_id, lab_id, data jsonb, updated_at)`. Photos of signed-in students are also stored in the private bucket at `photos/<user_id>/<lab_id>/<photo_id>.jpg` (storage policy "student manages own photos", `supabase/photos.sql`); `ltBind` lists the lab's folder once, uploads device-only photos, downloads account-only ones, and in admin review mode shows the reviewed student's photos; Clear entries, account/seat/class deletion remove the folder (`removePrivatePrefix`).
- Entry keys are widget ids: `<id>` for answers/notes/inputs, `<table>.r<row>c<col>` and `<table>.rows` for tables, `<steps>.step<n>` for step notes, `data-check` ids for checkboxes. Legacy `report.<id>` keys exist from before 2026-09-25.
- Automatic ids are positional per kind (`q1`, `table1`, `proc1`, `notes1`, `photo1`, `field1`); explicit `id=` never changes after the first save.
- Merge rule: whole-object, newer `_savedAt` / `updated_at` wins.

Release rule: before every push that touches the renderer, `ltBind`, the report code, or the builder model, run `entriesSelfTest()` in the preview (it must return true) and re-run the saved-work guard checks (`labWorkProblems`) against a lab with entries.

## Guardrails

- **Never open student entries (owner's hard rule, 2026-11-20).** "Never open student entries. You can run the script that does site backup, but no reading the student entries directly." This covers every route: the admin review screens in the owner's Chrome, queries on `lab_entries`, the files under `Lab Site Backups/`, the photos bucket. `node scripts/backup.mjs --verify` may be run; read only the counts it prints. Test with made-up data in the local preview; to diagnose a student's problem, ask the owner to describe it. Reason: anything an assistant opens becomes part of its conversation and leaves the site, which the Privacy page does not describe. Treat students' photos, tutor conversations, help messages and Google names and emails the same way (the assistant's reading of the rule, not the owner's words). No earlier or general permission overrides this; only the owner can lift it.

- **Link the format guide after every push that changes it (owner's rule, 2026-11-17).** When a push changes `docs/LAB-FORMAT.md` (or `docs/socratic/BANK-FORMAT.md`), the reply that reports the push ends with the link to the file on GitHub, so the owner can hand it to his lab-design session: https://github.com/Duct-Tape-Magic/lab-site/blob/main/docs/LAB-FORMAT.md and https://github.com/Duct-Tape-Magic/lab-site/blob/main/docs/socratic/BANK-FORMAT.md
- **Backup before every risky push (owner's rule, 2026-10-26).** Before pushing anything that touches student entries, photos, ids, the local/cloud merge, sign-in adoption, Clear entries, or deletion: run `node scripts/backup.mjs --verify` and paste its printed counts into the chat. Stakes: ~49 students, ~3 h per lab; one bad push can erase more hours than the site took to build. Ship such changes outside lab hours.
- **Edit lists (owner, 2026-11-22): no editor may ever reach student data, and none may change who sees or who edits a lab.** (The rule comes from the owner's beta-mode instructions of 2026-11-21: "No beta users should ever be able to access student data", "they should not be able to control who sees the labs that they publish".) Edit rights exist only as the narrow functions in `supabase/editors-2026-11-22.sql`; never give editors a table policy, and never build an edit check on `is_admin()` or `item_visible()` (both say yes to admins). Being on an edit list must never widen what someone can see. When adding a lab or folder column, decide whether `editor_save_lab` may write it (default: no). When adding a table that holds student work tied to a lab, add it to the refusal in `editor_delete_lab`. After any change to that file run `supabase/editors-test.sql` in the SQL editor.
- **Everything a lab author writes goes through `safeHTML()` before it reaches the page** (the output of `ltRender`, a rich-text procedure, the rich-text editor loading a lab). A new place that shows lab content must do the same. A value put inside a quoted string in an `onclick="…"` needs `jsAttr()`, not `escapeHTML()`. The renderer's own markup must not rely on `id=`, `on…=`, `<svg>`, `<style>` or `<form>` inside a pane, because the cleaner removes them; ids added after the pane is on the page (by `ltBind` and friends) are fine.
- **Backups expire after 30 days, and the Privacy page says so (owner, 2026-11-21).** The point is that a student who deletes their account is gone from the backups too. The Privacy page's last sentence ("Backups are deleted after 30 days.") and `KEEP_DAYS` must change together. Keep backups out of Dropbox, iCloud and any other synced or shared folder: a service that keeps its own copy breaks the promise. The newest verified backup is never deleted, however old. Expiry deletes backups, never anything on the live site. If `node scripts/backup-schedule.mjs status` says the schedule is not running, tell the owner.
- **Every new table needs an explicit Data API grant** (Supabase stopped granting them automatically on 2026-10-30): after `create table public.x`, add `grant select, insert, update, delete on public.x to anon, authenticated;` (and `grant usage, select on sequence …` for identity columns), then enable RLS and write the policies as usual. `supabase/grants.sql` re-grants every public table and is run after `schema.sql` on a fresh project.

- Keep the `<meta name="robots" content="noindex">` tag: the owner decided (2026-10-10) the site should not appear in search results; students reach it by link.

- Keep `index.html` single-file with vendored libraries; no build step; never add a CDN script.
- Never commit the service key. The publishable key belongs in `CONFIG` and in Action secrets only.
- Every student-facing string goes through `getText`/`fmt` so the owner can edit it.
- All owner settings persist to Supabase (`site_content`), never localStorage (localStorage is only for caches and per-visitor conveniences).
- Keep the fallback chain working: any new public data must also be included in `scripts/snapshot.mjs` and `applyCatalogue()`.
- Locked content must never be readable without the gate: check RLS before exposing any new table.
- Default new visual features OFF so the owner's saved look never changes unexpectedly.
